Concierge Revision · Phase 3 · Mock for sign-off

No self-serve refund — a revision, then a real dispute path.

P1 gave every buyer one consultation + one revision from their expert. P3 finishes the migration: it replaces the buyer's self-serve refund button with a two-step recourse ladder, and gives admins a ready-made dispute queue whose refund is the escape hatch. The self-serve refund is only removed after that recourse exists.

"No refunds, but allow the user to request one modification from the expert… experts should offer one consultation and modification with every ready-made trip. Then we can eliminate the refund." — plus "Keep the admin escape hatch." Decision-maker, ratified this session · phased build P1 (merged) → P2 (merged) → P3 (this mock)

01

The recourse ladder

Removing the refund button is only safe because two forms of recourse sit in front of it. A buyer never hits a dead end — they escalate one rung at a time, and money-back still exists at the top, now with a human deciding it.

Rung 1 · self-serve

Request the revision

Buyer asks their expert to adjust the plan for their dates & taste — right from the Trip Slip. Grants the expert write access to the clone. Already shipped in P1/P2.

Buyer → Expert
Rung 2 · self-serve

Get help with the purchase

Still not right? The buyer opens a concern. It becomes a dispute row for admin review — no money moves yet, and the honest copy never promises a refund.

Buyer → Admin queue
Rung 3 · escape hatch

Admin refunds or dismisses

An admin reviews the dispute — seeing whether the revision was even used — and either refunds the buyer (reversing earnings + revoking the clone) or dismisses it.

Admin decides

Why this order. The self-serve refund can't be removed until the thing replacing it exists. So P3 builds rungs 2 & 3 first; the button removal (§3 below) is the last edit to land, and only once an admin can still make a buyer whole.

05

Data model & governance

The dispute concept is net-new for ready-made purchases (today it only exists for service bookings). It lands additively, following the house rules.

migration · additive

Three nullable columns on ready_made_purchases

dispute_status (null = none · open · resolved_refunded · resolved_dismissed), dispute_reason text, disputed_at. Declared in shared/schema.ts, no DB CHECK, migration registered — publish-trap rule.

L6 · one implementation

The refund ledger gets a second caller, not a rewrite

refundReadyMadePurchaseLedger gains an actor param. Buyer path is unchanged; admin path bypasses the buyerId + window gates. No parallel refund code.

§14 · server-derived

Amount & actor never come from the client

Refund amount is read from the purchase row; the admin actor is proven by session role (user.role === "admin"), exactly like the existing dispute-uphold route.

§19 · allowlist

Dispute fields are not client-writable

Buyers set dispute_reason through the concern endpoint only; dispute_status transitions are server-owned. Admin resolution is audit-logged like every other money action.
