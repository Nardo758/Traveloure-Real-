You are a Senior QA Engineer, formerly at Amazon, running the Tier 3 
audit on Traveloure — correctness under real usage. This tier isn't 
about security bypass, it's about whether the product actually does 
what it claims under real-world edge cases. This is a LOOP, not a 
single pass. Keep testing each surface with fresh randomized input 
until it goes clean twice in a row, or you hit the loop cap.

============================================================
GLOBAL RULES
============================================================
1. No test is "pass" without live evidence — actual request/response, 
   actual DB state, actual rendered output, actual timestamp/timezone 
   value. "Should be correct" is not evidence.
2. Every loop uses NEW randomized input — different dates, timezones, 
   locales, price ranges, search terms, prompt phrasing. Don't repeat 
   the same test data twice.
3. Bug found → fix it → re-run the exact failing case + 2 variations 
   → only then mark closed.
4. Track a LOOP COUNTER per surface. 2 consecutive clean loops with 
   varied input = surface CLOSED. 6 loops without closing = STOP, 
   flag as STRUCTURAL RISK for manual review, move to next surface.
5. Report loop-by-loop as you go, with evidence, not just a final 
   summary.
6. This is a correctness audit, not a security audit — do NOT touch 
   production data or send real emails/notifications during testing; 
   use the same safe dev-environment discipline as Tier 2.

============================================================
SURFACE 1 — AI ITINERARY GENERATION (abuse + correctness)
============================================================
Randomize per loop: prompt phrasing, destination, trip length, 
language, adversarial technique.

- Hallucination check: generate itineraries for real destinations and 
  verify at least a sample of named places/venues actually exist and 
  are plausible (not fabricated). Vary destination each loop.
- Prompt injection: attempt to get the AI to reveal its system 
  prompt, ignore instructions, or output something outside the 
  itinerary format — rotate injection technique each loop.
- Nonsense/adversarial input: gibberish, contradictory constraints 
  (e.g. "3 day trip to nowhere," negative trip length), extremely 
  long input.
- Cost-abuse: rapid repeated generation requests from one account — 
  confirm the bound found/added in Tier 2 actually holds under real 
  repeated use, not just a single test call.
- Confirm generated itinerary times/dates are internally consistent 
  (no overlapping activities, no impossible travel time between 
  venues).

============================================================
SURFACE 2 — TIMEZONE HANDLING
============================================================
This is a classic travel-app bug class — test it hard, randomize 
timezone pairs each loop.

- Booking created by a customer in timezone A for a provider/expert 
  in timezone B — confirm displayed times are correct and consistent 
  for BOTH parties, not just stored correctly server-side.
- DST transition edge cases — book a slot that falls on/near a DST 
  change date, confirm no hour-shift bug.
- Confirmation emails/notifications show the correct local time for 
  the recipient, not a shared/server timezone.
- Cross-timezone cancellation cutoff — confirm the cutoff enforcement 
  uses the correct timezone reference (whose "24 hours before" is it?).

============================================================
SURFACE 3 — SEARCH / DISCOVER / FILTERS
============================================================
Rotate filter combinations each loop, including deliberately 
contradictory or extreme ones.

- Boundary values: price range at exactly min/max, date range of 
  zero days, date range spanning years.
- Empty-result state: confirm it displays correctly, doesn't error, 
  doesn't silently show unfiltered results instead.
- Combined filters (price + date + category + location together) — 
  confirm results actually satisfy ALL filters, not just the last one 
  applied.
- Special characters / unicode in search query — confirm no crash, 
  reasonable behavior.
- Confirm filter state persists correctly across pagination.

============================================================
SURFACE 4 — CANCELLATION & REFUND POLICY ENFORCEMENT
============================================================
Randomize timing relative to cutoff each loop — this must be tested 
at the code level, not just the displayed policy text.

- Cancel exactly at the stated cutoff boundary (before, at, after) — 
  confirm the actual refund amount matches the stated policy, not 
  just that cancellation succeeds.
- Confirm the enforcement is server-side (attempt to trigger a 
  full-refund cancellation past the cutoff via direct API call, not 
  just through the UI which might just be hiding the button).
- Multiple cancellation attempts on the same booking — confirm 
  idempotent, no double-refund.
- Provider-initiated cancellation vs customer-initiated — confirm 
  correct policy applies to each (often asymmetric).

============================================================
SURFACE 5 — REVIEW SYSTEM INTEGRITY
============================================================
- Attempt to submit a review without a completed booking — confirm 
  server-side block, not just UI hiding.
- Duplicate review on the same completed booking — confirm blocked 
  or correctly treated as an edit, not a second review.
- Review edit/delete permission — confirm only the review's author 
  (or admin) can edit/delete it, randomize attempting as a different 
  user each loop.
- Rate limiting / review-bombing resistance — rapid review submission 
  from one account across multiple bookings.
- Rating aggregate calculation — confirm the displayed average 
  actually recalculates correctly after a new review, an edited 
  review, and a deleted review.
