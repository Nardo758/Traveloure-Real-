# Execution Protocol — closing the decision→execution gap

**Status:** Dispatch for Claude Code. Small lane: create the ledger, retrofit brief headers, slim CLAUDE.md, wire the checklist. Phase 0 inventory (§7), HARD STOP, then execute. This document is itself durable content and follows its own rules.

---

## 0. The problem

Decisions are made in a stream (working conversations, merging lanes); execution reads from snapshots (briefs, CLAUDE.md, audit maps). Snapshots decay the moment the stream moves, and with concurrent agents the stream moves daily. Three consecutive audits found materially stale specs (dispatch vs. optimizer read path; role map vs. landed L10 fixes; 4 of 6 console-sigma flags already dead). The cost is paid in Phase 0 re-verification, near-miss rebuilds of landed work, and rulings that exist only in conversation history. Root cause: documents mix **durable** content (decisions, invariants) with **volatile** content (current-state claims) and nothing forces the volatile parts to update when code changes. Every artifact guarded by CI (mint-path tripwire, fee-literal grep, matrix lint) has never gone stale; everything enforced by prose has. The fix converts prose to mechanism wherever possible and bounds the rest to one merge cycle.

## 1. The durable/volatile rule (binding on all briefs from adoption)

- **Durable content** — decisions, contracts, invariants, prohibitions, scope boundaries. True until explicitly amended. Lives in briefs, the contract docs, and the ledger.
- **Volatile content** — any claim about the current state of code, schema, data, or defects ("X is cart-based", "flag #2 exists", "N paths leave this NULL"). True only at a SHA.
- Rules:
  1. Every brief header carries `audited@<main-sha>` (and `spec@<sha>` when auditing another doc).
  2. Volatile claims inside briefs are tagged `as-of <sha>` where load-bearing, and agents treat ALL volatile claims as hypotheses: **every Phase 0 opens by diffing the brief's state claims against current main** and recording deltas as findings before anything else. (This formalizes what agents have been doing instinctively.)
  3. Briefs cite ledger rulings by number instead of restating them — restatement is where paraphrase drift enters. A brief may quote a ruling verbatim with its number; it may not paraphrase one.
  4. Code is ground truth over every document; ledger is ground truth over every brief; a ledger-vs-code disagreement is a finding, never a silent divergence.

## 2. The decision ledger — `docs/DECISIONS.md`

Append-only. One line per ruling: number, date, decision, amends-pointer if any, context link (brief/PR/conversation-derived doc). Amendments are new entries pointing back (as ruling 18 amended ruling 12) — never edits. When a spec and the ledger disagree, ledger wins.

## 3. Ruling classification — every new ruling gets one tag at creation

- **`[guarded]`** — enforceable by a cheap machine check (grep gate, tripwire script, lint, CI assertion). The guard ships **in the same lane** as the ruling's implementation; the ledger line names the guard.
- **`[advisory]`** — judgment/process rulings; ledger only.
Existing guarded set (name-checked so agents don't re-invent): fee-literal grep · apply-never-writes-routing_status grep · mint-path owner tripwire · trackingNumber tripwire (17) · matrix lint w/ expiring deferred tags · chain-integrity test. Convert-candidates for this lane's follow-up list: single-writer-per-event-type (11), log append-only route inventory (N12), no-second-scheduling-heuristic (22 remediation), env allowlist. The `deferred:` expiry mechanism is the standard staleness-forcing device — spread it to expected-fail assertions (21) and, where practical, to `as-of` brief claims.

## 4. Merge write-back checklist (append to every lane's merge gate)

On every merge to main, the lane's PR must include:
1. CLAUDE.md delta for any state its merge changed (or explicit "no delta").
2. Expiry of any `deferred:`/expected-fail tags this merge satisfies.
3. One-line `superseded@<sha>` annotation appended to any brief section whose volatile claims this merge invalidated (annotation, not rewrite — the original stays legible).
4. Ledger append if the lane executed or amended a ruling (implementation reference added to the ruling's line).
Cost: ~30 seconds per merge. It replaces read-repair (audits discovering drift) with write-through.

## 5. CLAUDE.md slimming spec

CLAUDE.md becomes an index, not a narrative: invariants + pointers (ledger, contract docs, lane board, guard list) + the thin operational notes agents genuinely need at boot. It contains NO restated rulings, NO defect status ("fix in flight" class is banned — defect state lives in findings docs with `as-of` SHAs), NO duplicated spec content. Target: agents read it in one screen and know where truth lives.

## 6. Honest bound

This protocol does not eliminate drift; it bounds it to ≤ one merge cycle and makes it self-announcing (expired tags, failed guards, Phase-0 diff findings) instead of audit-discovered. Concurrency cap (two lanes) remains a load-bearing part of the bound — staleness velocity scales with parallel lanes.

## 7. Phase 0 (read-only, HARD STOP)

1. Inventory all live briefs/specs in docs/: current header state, which contain volatile claims, which restate rulings (candidates for cite-by-number replacement).
2. Reconstruct `audited@sha` for each live brief from git history where determinable; where not, mark `audited@unknown` (honest) for refresh at next touch.
3. Inventory existing guards (script + CI job list, file:line) vs. §3's name-check; list gaps.
4. Current CLAUDE.md content classified: keep-as-index / move-to-ledger / move-to-findings / delete-as-stale.
5. Return findings for approval before touching any file.

**Phase 1 scope (after approval):** create DECISIONS.md seeded per §2 · retrofit headers · slim CLAUDE.md per the approved classification · add §4 checklist to the PR template · matrix-lint-style ledger lint (every `[guarded]` ruling's named guard exists in CI).

## 8. What NOT to do

- Do NOT rewrite historical briefs to "fix" stale claims — annotate with `superseded@sha`; history stays legible.
- Do NOT edit or delete ledger entries — amendments are new entries.
- Do NOT paraphrase rulings into briefs — cite numbers, quote verbatim if needed.
- Do NOT build heavyweight tooling (no databases, no dashboards) — the protocol is markdown + tiny lint scripts, same weight class as the mint tripwire.
- Do NOT let this lane absorb any guard-conversion follow-up beyond the ledger lint itself — convert-candidates are named follow-ups.
- Do NOT treat a green protocol as eliminating Phase 0 diffs — the opening diff ritual is permanent.
