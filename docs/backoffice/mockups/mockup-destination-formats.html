Destination formats: the build stops being one Trip Card

Every build currently renders as the same day-list card — a Kyoto temple route, a Kyoto wedding, and a generic city break are structurally identical. This spec gives each destination × experience type its own format, in the builder and on the store page the buyer sees.

1 · How a build picks its format

No new data is stored. The format is derived from two fields every build already has — destination and experience type — through a fallback chain, so every existing build keeps rendering exactly as today until a more specific format matches.

(destination, type)→ destination default→ type default→ travel-generic (today's card)

travel-generic is the current PlanCard. Formats are pure client resolution — no schema change, no migration, improvable without touching data. New markets get a format when they open (§12).

Decisions this mockup encodes

Both axes, ratified.

Format = destination × experience type. Kyoto formats first (kyoto-cultural, kyoto-wedding); event-generic covers events elsewhere; travel-generic is the unchanged fallback.

Builder and store share one format.

The format is part of the product — the expert authors in it, the buyer previews in it. One registry, two consumers, no fork.

Derived, not stored.

Resolved from trips.destination + eventType at render time. No migration, no publish-push trap. Pinning a format per build becomes an additive column only if ever needed.

Honest slots (§13).

Seasonal notes, maps, and counts render only from real data; unmapped items land in a visible generic section, never dropped or invented.

Build order.

F1 registry + extract travel-generic (behavior-identical refactor) → F2 kyoto-cultural → F3 kyoto-wedding + event-generic → F4 store pages consume format layouts.
