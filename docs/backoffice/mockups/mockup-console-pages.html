3c · The creation ladder — /earn to a bed & breakfast

One door that grows with the merchant. Each rung reuses the one below it — never a new tool — and every rung's output enters the same rails: approval queue, storefront, Calendar, Distribute.

Selection only "I host guests" · "I run tours" apply → admin approval

Rung 1 · First service

ServiceForm Gion evening food walk offering pre-selected from /earn

Rung 2 · A catalog

Room · Breakfast · Airport transfer each with availability

Rung 3 · A bundle unlocks at 2+ approved services

Bundle Riverside Escape — room + breakfast + tour one price · same approval queue

Rung 4 · The B&B

Property Machiya guesthouse photos · per-night · room calendar
1 property + N services + M bundles = one storefront, one Calendar, four channels
Progressive reveal, honest gates. Bundle appears only when there are two approved services to compose (nothing to teach, nothing locked-and-teased); components must be approved (an unapproved service can't hide inside a sellable bundle — the F2 read-gate lesson). The same admin queue reviews every rung — no parallel approval machinery.

Decisions this mockup encodes (for ratification)

Calendar = the 9th module, amending §17's 8.

One calendar, channel-filtered — never per-channel calendars. Inbound/outbound/availability/store-lifecycle event taxonomy as legended above.

Every calendar event is a real row.

Slots, bookings, requests, purchases, delivery steps, listing transitions, coordination dates — all live tables today. Social scheduling joins only when the kit really schedules (§13: the lane renders empty until then).

The calendar references, never re-renders.

Clicking an event opens its owning module (one home per datum — the §17 programming rule).

17 → 9 by absorption, not deletion.

Every retired entry redirects into its absorbing module; no action or list is lost. Open taste calls: Messages (Inbox queue vs utility row) and AI Assistant.

Catalog = the storefront's management home.

/p/:handle is already the public store across ALL lanes (Ready Made is one shelf); Catalog gains the link/preview header and the availability editor that feeds the Calendar.

Customers is honest aggregation.

Derived from this earner's real bookings/purchases/ trips; self-scoped; no invented CRM fields without ratification.

Provider = nine modules too — Workstation is the Product Builder.

Corrected from "provider minus Workstation": providers compose PRODUCTS — bundles (own services packaged with one price), single tours, properties (accommodation + photos + per-night pricing + availability). Same build-first/ distribute-later spine; the social kit renders the package ad from real components.

Bundle product type needs schema ratification before build.

provider_services stays canonical (no new service table — the FAQ prohibition); a bundle is a provider_services row whose COMPONENT linkage (join rows or jsonb) is a decision-maker schema call. Booking a bundle = ONE server-derived price from the stored product (§14), one booking row, component fulfillment behind it — the money design gets its own brief before any code.

Build order (PR-C).

C1 sidebar collapse + redirects (deletion-first, cheapest) → C2 Catalog storefront header + availability move → C3 Calendar (read-only aggregate first, slot-editing links out) → C4 Customers → C5 Money rename + Settings/Profile merge → C6 provider 9-module stamp. The provider Product Builder (bundles/properties) is its OWN lane after PR-C, gated on the bundle schema ratification.
