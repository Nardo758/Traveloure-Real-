# W0.7 — Review-response moderation blind spot

**Tier:** Sonnet. **Migration:** none (a response *status* column is optional — see scope). **Est.:** ~50k tokens.
Filed: FOLLOWUPS **M4**.

## Defect (verified)

`POST /api/expert/reviews/:id/respond` (`server/routes.ts:4299`, owner-gated) writes via
`storage.addReviewResponse` (`server/storage.ts:1647`), which sets `responseText` + `responseAt` directly —
**the provider/expert reply publishes live immediately, with no moderation state.** The admin review-moderation
queue is blind to responses: `ModerationReview` (`client/src/pages/admin/review-moderation.tsx:26-38`) carries
only rating/reviewText/status/flagReason, and the `getAdminReviews` enrichment (`server/routes/admin.routes.ts:4806`)
never includes `responseText`. The only admin lever removes the **entire** review — which also deletes the
traveler's legitimate review (the wrong tool). Since "Reviews" becomes a first-class backoffice nav item that
*encourages* responding (W0.x / N7), this gap must close first.

## Scope

1. **Surface responses to admins (read):**
   - Include `responseText` (+ `responseAt`) in the `getAdminReviews` enrichment (admin.routes.ts:4806).
   - Add `responseText`/`responseAt` to the `ModerationReview` interface + render the response in
     `review-moderation.tsx` (clearly labelled as the provider/expert reply, distinct from the traveler review).
2. **Add a response-scoped action (moderate the reply WITHOUT touching the traveler review):**
   - A "Clear response" admin action: an endpoint that nulls `responseText`/`responseAt` on the row (reuse the
     `addReviewResponse` storage path or a sibling `clearReviewResponse`), owner = admin via `adminApiGuard`.
   - The existing full-review status actions stay for the traveler-review half.
   - **Optional (only if the decision-maker wants pre-moderation):** a `response_status` column so responses are
     held before publish. Default recommendation: **post-moderation** (publish live, admin can clear) — no
     migration, simplest, matches the current instant-publish behavior. If you add a status column, it's a
     migration (additive-nullable, no CHECK) — but prefer NOT to unless asked.

## Traps

- The "Clear response" action must NEVER delete or alter the traveler's `reviewText`/`rating` — only the
  response fields. Assert this in the gate.
- §14: admin identity from session via `adminApiGuard`; no body-supplied ids into the decision.
- Do NOT change the expert respond endpoint's behavior (experts still respond); this brief adds admin
  *visibility + a clear lever*, not a new response workflow.

## Gate

- Four standard gates.
- Behavioral: (a) `GET /api/admin/reviews` returns `responseText` for a review that has one (fails on pre-fix,
  which omits it); (b) the "Clear response" action nulls the response but leaves `reviewText`/`rating` intact
  (assert both); (c) non-admin cannot call the clear action (401/403).
