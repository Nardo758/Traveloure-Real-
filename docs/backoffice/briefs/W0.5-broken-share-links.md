# W0.5 — Broken generated share links

**Tier:** Haiku. **Migration:** none. **Server changes:** none. **Est.:** ~10k tokens. Filed: FOLLOWUPS **K1**.

## Defect (verified)

`client/src/components/booking/VariantActionButtons.tsx:249` builds share links as `/shared-trip/${token}`,
but `client/src/App.tsx` registers no such route — only `/trips/shared/:token` (App.tsx:344) and
`/itinerary-view/:token` (App.tsx:339). Every link generated by those share buttons (copy-link + the
Facebook/Twitter/WhatsApp/email intents built from it at VariantActionButtons.tsx:266-273, 531, 787) lands on
the SPA fallback instead of the shared view.

## Scope

Point the generated link at the **real** route. Determine which of the two registered routes the token is for
(read how the token is produced — the trip/variant share-token flow that App.tsx:344 `/trips/shared/:token`
serves is the likely target; confirm against the token's origin). Replace `/shared-trip/${token}` with the
correct registered path. Fix every occurrence in the file (the block is duplicated internally — grep
`shared-trip` within the file and fix all).

## Traps

- Verify by matching the token's producer to the consumer route — do not guess between `/trips/shared/:token`
  and `/itinerary-view/:token`; read where `token` comes from in this component and pick the route whose page
  resolves that token type.
- The copied link is used verbatim in the wa.me / social intent URLs — fixing the base path fixes all of them;
  don't touch the intent-URL construction.
- Do NOT introduce a new route to match the old string — fix the string to an existing route.

## Gate

- Four standard gates.
- Behavioral: the link produced by the share action resolves to a registered route (assert the built URL's
  path matches an App.tsx `Route path` — fails on the pre-fix `/shared-trip/` string). A manual click lands on
  the shared view, not the SPA fallback.
