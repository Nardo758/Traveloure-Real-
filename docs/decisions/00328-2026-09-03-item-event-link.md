| 2026-09-03-item-event-link | 2026-09-03 | [advisory] | **AN ITEM BELONGS TO AN EVENT, AND THE EVENT IS A `user_experiences` ROW — `itinerary_items.user_experience_id` (migration 277).** The proposed model (FLOW-SPEC v2, ratified today) is: a plan = ONE `trips` row; each event inside it = ONE `user_experiences` row; every plan has ONE **implicit unnamed event** so items always resolve. **NO NEW TABLE, and none was needed** — `user_experiences` already carries a nullable `trip_id` with NO uniqueness (many events per trip) plus `event_date`/`location`/`budget`/`guest_count`/`experience_type_id`; invites already hang off an event (`event_invites.experience_id`); a temporal anchor already can (`temporal_anchors.user_experience_id`); and the slip already MINTS one row per trip on "set up guest list" (`SlipLogisticsSection` → `POST /api/user-experiences`). The ONE thing missing was the link the other direction, from the ITEM to the event. (The `userExperienceId` columns already in `shared/schema.ts` belong to OTHER tables — `user_experience_items`, `temporal_anchors`, `event_invites`' sibling — `itinerary_items` had none.) **THE COLUMN:** additive, NULLABLE, **NO DB CHECK** (migration-181/195/275 posture — a CHECK is the publish-time drizzle-push failure the Coordination Prevention rules name), FK `REFERENCES user_experiences(id) **ON DELETE SET NULL**`, plus `idx_itinerary_items_user_experience_id`. **COLUMN AND INDEX ARE DECLARED IN `shared/schema.ts`** — the deploy-push durability rule: an object this file does not declare is DROPPED at publish and never recreated, because the migration is already stamped. **ON DELETE SET NULL IS THE RULING, NOT AN FK DEFAULT:** deleting an event must NEVER delete the items planned under it — they fall back to the plan's implicit event and stay on the traveler's slip. A CASCADE would let removing a "Rehearsal dinner" card silently destroy every item beneath it (N2 pins this). Equally, **NULL is not "unknown"**: NULL *is* the implicit event, which is why no backfill is owed and why nothing may be guessed into it (§13). **ADMISSION IS A §19 ALLOWLIST, not a widened denylist.** `insertItineraryItemSchema` `.omit()`s `userExperienceId` and a **pick-based** `itineraryItemEventLinkSchema` re-admits exactly that one field, `.nullish()`. This is §19 applied to a NEW column rather than retro-fitted to an old one: under a denylist schema a freshly-added column is client-settable BY DEFAULT ("nobody edits an omit list for a column that did not exist when it was written") — and this one names a row in ANOTHER table. The `.pick()` does not move `check-omit-schema-ratchet.cjs`'s baseline (held at **187**); a pick is not counted. **THE PAIRING IS SERVER-VERIFIED (§14), AND THE VERIFICATION IS ONE MODULE.** Shape is all the schema proves. `resolveItemEventLink` (`server/services/item-event-link.service.ts`) re-reads the `user_experiences` row and refuses with a 400 unless it EXISTS and its `trip_id` equals the ROUTE's `tripId`. The route's own authorization answered "may this caller write to THIS trip"; it said nothing about the id in the body, and owning both plans still must not let you file an item under the other plan's event (N1 uses a same-owner second trip precisely so this cannot be mistaken for an ownership check). Unknown-id and cross-trip return the SAME message so the endpoint is not an existence oracle. **TWO CALLERS, ONE IMPLEMENTATION:** the live `POST /api/trips/:tripId/itinerary-items` — the **`server/routes.ts` monolith copy**, which registers first and SHADOWS the `trips.routes.ts` twin (§9) — and the live `PATCH /api/trips/:tripId/itinerary-items/:itemId` (`trips.routes.ts`, no twin in routes.ts). A second copy of the same admission is the derivation-drift class §18 rule 1 names, so the **shadowed POST twin is ANNOTATED, not duplicated** (the migration-275 precedent). Writes gate on the same §12 advisor WRITE statuses as every other item mutation; the PATCH's raw destructure strips `userExperienceId` (layer 1) before the resolver re-admits it (layer 2). **ABSENT ≠ NULL ≠ A VALUE**, all three kept distinct end to end: absent ⇒ leave the link alone; `null` ⇒ back to the implicit event; a value ⇒ verify, then set. **READ EXPOSURE:** `GET /api/trips/:tripId/itinerary-items` carries the column with NO mapping change (it emits the rows themselves, so declaring the column is what puts it on the response — recorded in the handler so nobody "adds" it twice); the plancard activity DTO carries `userExperienceId` **present-only-when-set** (absent key, not a null one — the `booking`/`affiliateBooking` posture, so every unlinked item is byte-identical to before); and the plancard payload gains an **`events`** array (id, title, eventDate, location, guestCount, experienceTypeId). **`events` IS RESOLVED IN THE PLANCARD HANDLER, NOT IN `assembleTripPlan`** — deliberately: the assembler serves three redaction levels including the PUBLIC share/teaser channels, and an event carries a guest count, a budget and a venue. Resolving it in the handler means it is gated by exactly the owner/assigned-advisor/author check already there and can never leak into a channel that never asked for it. A plan with no `user_experiences` row returns `[]`, the honest "only the implicit event" state, never a fabricated placeholder. **SAME LANE, THE RE-MASK FIX (§13):** `EditTripPanel` seeded its travelers input with a literal `2` and wrote `travelers` on EVERY save, putting migration 241's de-masking back one layer up — a traveler who opened the panel to fix a title left with a **fabricated party of two**, indistinguishable downstream from a stated one. Now: untouched ⇒ NOT SET. The input holds a STRING so the empty state is representable, seeds EMPTY when no count is stored, and the save routes through one pure normalizer, `travelersForSave` (`client/src/lib/plan-vocabulary.ts`) — empty/whitespace/zero/negative/unparseable ⇒ `undefined`, and `switchTripContext`'s REPLACE semantics then CLEAR the field rather than re-asserting a guess. The old `Math.max(1, parseInt(…) || 1)` onChange (which turned an empty box back into a 1) is gone. **NEGATIVE SPACE (ruling 43) — deliberately NOT done:** NO client grouping UI. The slip does not group by event, there is no "Which event?" picker on Add-to-Plan, no per-event panels and no `events` chip on the Trip Strip — this lane lays the column, the verified write rails and the read exposure a grouping lane will consume, and nothing more. NO `trip_destinations` table (FLOW-SPEC's other proposed column — a separate ratification). NO backfill and no `experience_types` default columns. NO CHECK, no DEFAULT, no fee/rate literal. `event_invites`, `temporal_anchors` and `user_experience_items` are untouched. The shadowed POST twin in `trips.routes.ts` is left shadowed. **PROOF:** `server/__tests__/item-event-link.db.test.ts` — N1 cross-trip refusal (400, link AND title byte-unchanged, on the REAL mounted PATCH router and on the shared resolver the POST rail calls), N2 event-delete ⇒ link NULL + item survives, P1 same-trip create carries it (allowlist admits exactly one field), P1b absent-vs-null on the live rail, P2 the plancard lists the events and the activity points into them. **Bench suite, NOT CI-wired** (house `*.db.test.ts` posture; the `routes.ts` monolith is not a mountable router, so P1 proves the admission and the write, not that handler's express wiring — the shared resolver is what carries the proof across).
