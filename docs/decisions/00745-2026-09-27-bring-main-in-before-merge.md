| 2026-09-27-bring-main-in-before-merge | 2026-09-27 | [advisory] (RECORD ROW — a merge habit, no code, no schema, no test. `mergeable_state: behind` is visible on every PR read; nothing enforces the re-run half, and this row says so rather than naming a guard it does not have.) | **R171 — BRING MAIN INTO THE BRANCH BEFORE MERGE; RE-RUN CI WHEN THAT MERGE TOUCHES FILES THE PR CHANGED (decision-maker, Sep 27, 2026).** A PR that is behind `main` is merged only after `main` has been merged INTO its branch (a merge commit, never a rebase or force-push on a branch someone else owns — the Driving-a-PR-to-green rule). When the incoming `main` changes any file the PR itself changes, the green CI from before that merge proves nothing about the combination, so the PR waits for its OWN branch's CI to go fully green again on the new head before it is merged; the standing rule that a PR is Ready only after its own branch CI is fully green applies to that head, not the earlier one. When the incoming changes and the PR's files do not overlap, the required checks still run on the new head as branch protection demands. The merge itself uses the `merge` method with `expectedHeadSha` set to that verified head, so a push landing between the check and the merge refuses the merge rather than shipping an unverified head. **Why:** the same-day ledger collisions and the `mergeable_state: behind` PRs (#1132, #1134) showed a green check on a stale base is not evidence about the merged result. | numeric citation R171; R169 |
