That was safe only because the owner was the sole possible payer: two concurrent calls carried the SAME idempotency key, so Stripe returned ONE intent and there was ONE charge. The moment a second payer exists the key MUST differ by actor, so two concurrent payers would create TWO intents and, on that branch, **take TWO REAL CHARGES for one balance** — which no post-call stamp can undo. So §15's own instruction is followed literally: claim the row atomically FIRST, then make the external call. One statement, `status='deposit_paid' AND stripe_balance_intent_id IS NULL AND COALESCE(recorded_payer, me) = me`, which admits an unclaimed row and the holder's OWN retry (the claim is idempotent, so §15 layer a is untouched) and matches zero rows for anyone else — who is refused **409 `balance_payment_in_progress` without Stripe ever being called**. Two related holes closed with it: the "balance already started" early return and the post-stamp fallback are now **payer-scoped**, because handing an existing balance PaymentIntent to a DIFFERENT user is not idempotency but cross-account — the intent was created against the first payer's Stripe customer with `setup_future_usage`, so a second person confirming it would charge their card AND vault it on someone else's customer; the stamp itself also narrows to the claim holder (defence in depth, not a second copy). A stamped row with NO recorded payer is a pre-ruling stamp, which only the owner could have made, so the owner still gets it back and nobody else does — an absent record is never read as "it must have been you" (§13). **NOTHING EVER RELEASES A CLAIM, and that is the ruling, not an omission:** `createPaymentIntent` RETURNS (rather than throws) whenever Stripe attaches a PaymentIntent to the error, so a THROW is exactly the case where we cannot prove one does not exist — releasing there is §15b's "never void a row whose PaymentIntent may exist", one leg over. A claim clears only when the balance is actually paid. The cost is a **LIVENESS limit, never a money-safety one**: a payer who claims and walks away holds the leg, and the owner is answered `balance_payment_in_progress` until they finish — and it self-heals for the one person it affects, whose retry rebuilds the SAME key and gets the SAME intent. **A TTL reclaim is PHASE TWO's**, where a real split needs an expiry model anyway. **THE IDEMPOTENCY KEY IS EXTENDED, NOT REPLACED:** `bal-<bookingId>` → `bal-<bookingId>-<payerUserId>` (`buildBalanceIdempotencyKey`). This is not cosmetic — `createPaymentIntent` builds the PaymentIntent FROM THE ACTOR (their Stripe customer, email and saved card), so one key presented with two different actors is one key with different parameters, which Stripe answers with an error or, worse, by handing the second payer the FIRST payer's PaymentIntent — a charge against the wrong person's card. The property §15 layer a depends on is preserved exactly: ONE payer retrying/double-clicking still rebuilds the SAME key and gets the SAME single PaymentIntent.
