| 2026-09-04-event-order | 2026-09-04 | [advisory] (`client/src/lib/__tests__/which-event.test.ts` W6, `server/__tests__/user-experience-order.test.ts` O1-O3) | **ONE CANONICAL ORDER FOR A PLAN'S EVENTS — `event_date ASC NULLS LAST`, then `created_at ASC`.** Decision-maker ratified Sep 4 2026. `2026-09-04-which-event-picker` shipped with rule 5 stating "ORDERING IS THE SERVER'S" — `eventsForTrip` filters without sorting and `whichEventChoices` preserves what it is handed — precisely so there would be ONE authority for it. That held on the client and failed on the server: `getUserExperiencesByTrip` (the plancard DTO, feeding the slip's event grouping) was already `event_date ASC NULLS LAST, created_at ASC`, while `getUserExperiences` (`/api/user-experiences`, feeding the picker via `eventsForTrip`) was `created_at DESC`. The SAME events therefore rendered in two different orders on two surfaces of the SAME plan — rule 5 defeated one layer down, which is the derivation-drift class §18 rule 1 names. **CHRONOLOGICAL IS THE RATIFIED ANSWER** (a plan reads forward in time; an undated event sorts LAST rather than jumping the queue on a NULL), and the fix is on the SERVER, in `getUserExperiences`. **A CLIENT-SIDE SORT WAS THE WRONG FIX AND IS FORBIDDEN:** sorting inside `which-event.ts` would make that module a second ordering authority — exactly what rule 5 exists to prevent — so rule 5's comment now NAMES the canonical order and says not to. **ONE LATENT COUPLING WAS SURFACED AND PRESERVED, NOT SILENTLY CHANGED:** `SlipLogisticsSection` picked its trip's event with a bare `.find`, which took whatever the endpoint returned FIRST — under `created_at DESC`, the most recently created. Re-ordering the endpoint would have quietly changed WHICH event that surface's guest list belongs to. It now sorts EXPLICITLY by `created_at DESC` and takes `[0]`, keeping today's behaviour exactly and removing the hidden coupling rather than moving it. **The ambiguity underneath is left OPEN on purpose:** migration 277 put no uniqueness on `user_experiences.trip_id`, so a plan can hold many events and "the plan's guest list" does not say which one it means; whether it should belong to the event the traveler minted it on is a product decision, not something to settle as a side effect of an ordering fix. | `experience-template.tsx` was already immune — it re-sorts by `createdAt DESC` explicitly before taking `[0]`. `trip-strip.tsx` takes only a COUNT off the list, so order cannot reach it. |
