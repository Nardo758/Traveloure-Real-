## What changed

### One home for the from-state lists (§18 rule 1)

`server/utils/booking-from-states.ts` (new). `OWNER_BOOKING_TRANSITIONS` **moved verbatim** out of the
`server/routes.ts` monolith (it was a local const inside `registerRoutes`, so no other file could reach it),
and the two new lists were declared beside it:

| constant | value | why |
|---|---|---|
| `OWNER_BOOKING_TRANSITIONS` | unchanged | SD-1 (ruling 42) |
| `DISPUTABLE_FROM_STATUSES` | `confirmed`, `deposit_paid`, `completed` | the paid-equivalent, completed-shaped states — the ones where money is in escrow for a dispute to hold back |
| `DISPUTE_REJECT_FROM_STATUSES` | `disputed` | the only state a rejection can put back is the one the dispute created |

`payment_pending` and `expired` are absent from **every** list, and the module says why in its own docblock:
a provisional claim's sole author is `checkout-claim.service.ts` (§15b), and moving one from anywhere else
strands the slot. `pending` is deliberately not disputable (nothing was charged, so a "dispute" there is a
cancellation wearing the wrong word); `cancelled`/`refunded`/`disputed` are excluded each for its own reason,
written down.

### V-23 — `POST /api/bookings/:id/dispute` (`server/routes/bookings.ts`)

Three-argument call → four. `undefined` is answered **409 `dispute_not_applicable`**, never `success: true`.
The `completed_at` window read above it is left exactly as it was and is now annotated as what it is: the
error message. It bounds a dispute in TIME; the UPDATE's own predicate bounds it in STATE.

### V-24 — `POST /api/admin/disputes/:bookingId/reject` (`server/routes/admin.routes.ts` + `server/storage.ts`)

- The handler now reads the booking for its own **404** (absent and wrong-state are different facts, §13),
  passes `DISPUTE_REJECT_FROM_STATUSES`, and **409**s a lost race with the current status named.
- `updateServiceBookingStatus` stamps `completed_at` as `sql\`COALESCE(completed_at, NOW())\`` — **in the SET
  expression**, so the single UPDATE stays the whole decision rather than becoming another read-then-decide.
  Two durable things anchor on that column (the traveler's dispute window via `holdWindowDays`, and through
  it the earnings-release timing), and an unconditional re-stamp restarted both.
- The mint stayed exactly where it is, inside the guarded UPDATE's transaction — which is why a refused
  reject mints **by construction**, not by a second check.

### V-25(b) — `storage.updateCoordinationStatus` + `PATCH /api/coordination-states/:id/status`

- `expectedFromStatuses` added as the **4th parameter, same shape and same position** as
  `updateServiceBookingStatus` (§18 rule 1 — delegated, not re-invented). Absent ⇒ previous behaviour verbatim.
- The `state_history` append is one SQL expression inside the same UPDATE:
  `COALESCE(state_history,'[]'::jsonb) || <entry>::jsonb`. Entry wrapped in an array so the `||` is an
  unambiguous array-to-array concat.
- The entry's `status`/`timestamp` are written **last**, so they are the server's answer, not a value the
  caller put in the free-form history body (§13). The rest of the caller's entry still lands.
- `completed_at` stamped only on the transition INTO completed.
- Both route arms pass `[fromStatus]` through **one** call site; a refusal is **409**.
- **V-25(a) is NOT fixed here.** The traveler arm still has no ordering rule. That is D-39's
  (`EXPERT_ACCEPTANCE_BRIEF` F3), and the code says so at the exact line where the from-state is passed.
  F6b pins both that the comment stays and that there is still exactly **one** `FORWARD_ORDER` list.

### No schema change

`coordination_states.state_history` is already `jsonb DEFAULT '[]'::jsonb`
(`server/migrations/000_baseline_schema.sql`), and `completed_at` already exists on both tables. **No
migration, no column, no CHECK, no index, no backfill.** `checkout-claim.service.ts`, fee/rate code and
`shared/schema.ts` were not touched.
