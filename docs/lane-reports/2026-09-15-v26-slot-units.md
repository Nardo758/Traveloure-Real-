# Lane report — V-26: slot claims and releases carry the line's unit count

Branch `task-v26-slot-units`, worktree `/home/user/wt-v26`, off `origin/main` @ `8da7259bf`.
Ledger slug: `2026-09-15-v26-slot-units`. Punchlist row: **V-26** (section 2).

## The defect (as filed)

`storage.bookSlot(id)` claimed exactly ONE unit of `vendor_availability_slots.booked_count` per
cart line whatever the line's unit count, and `releaseSlot(id)` mirrored it. D-14
(`2026-09-15-d14-quantity-is-units`) derives `quantity = party_size` server-side for the
seat-shaped `in_person`/`hybrid` archetype, so a listing that ASKS for seats charged for three
and debited the provider's calendar one.

## What this lane does

1. `bookSlot(id, units)` / `releaseSlot(id, units)` — ONE statement each; the capacity arithmetic
   AND the guard live inside it (`COALESCE(booked_count,0) + units <= COALESCE(capacity,1)`), so
   the statement IS the guard (§15/C3). Refused, never clamped. `units` must be a positive
   integer; 0 / negative / non-integer throws a NAMED error rather than defaulting silently.
2. Checkout (`payments.routes.ts`) passes the line's own unit count through the ONE derivation
   `resolveItemUnitCount(item)` — the same expression `resolveItemBaseAmount` multiplies by
   (§18 rule 1). The STAY branch passes `1` explicitly, with the reason in a comment (one slot
   per NIGHT, `quantity` pinned to 1 by D-14).
3. Release derives the units from what the claim RECORDED, not from what the line was priced at.

## Deviation from the brief, stated (§13), and why

The brief said the release should derive units from `bookingDetails.quantity`. That key is the
CART LINE's unit count, and for a row created BEFORE this lane it is NOT what was claimed: a
pre-fix booking carrying `quantity: 3` claimed exactly ONE unit, and releasing three would give
back capacity nobody took — the V-26 defect in the other direction, on a population that
demonstrably exists (D-14's V10 asserts a legacy `quantity: 3` stay row "which nothing rewrites").

So the claim spine RECORDS what it claimed — `bookingDetails.claimedSlotUnits`, the units taken
on EACH slot of `claimedSlotIds` — exactly as the RELEASE-ALL-NIGHTS hotfix already records
WHICH slots it claimed, and the release reads that. **Absent ⇒ 1**, because a pre-fix row claimed
one: never guess more than was recorded (§13). `deriveClaimedSlotUnits` sits beside
`deriveClaimedSlotIds` in `checkout-claim.service.ts` — ONE decider, every release path a caller
(§18 rule 1). The new key is server-authored, so it joins
`SERVER_AUTHORED_BOOKING_DETAIL_KEYS` (§19d) and B7's pinned set.

> **THE CLAIM'S SIZE IS PART OF THE CLAIM (ledger `2026-09-15-v26-slot-units`).** An inventory claim
> takes the quantity the line actually bought, and the arithmetic and its guard live in the SAME
> single statement (`booked_count + units <= capacity`) — a claim that adds a fixed 1 while the

> row (§13) and an absent record means the smallest claim that rail ever took.
