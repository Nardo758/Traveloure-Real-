# Traveloure automation discovery inventory

Audit date: 1 October 2026. Scope: source-code discovery across all requested backend domains, application startup, webhook dispatch, background jobs, request-triggered follow-on work, and external cron configuration.

No automation, database mutation, message, payment operation, or production job was executed. No application code, automation registry, deployment setting, or workflow was changed. Only this report was generated. Runtime configuration and actual scheduler/webhook delivery remain unverified. Source references are audit evidence, not proposed automation identities.

## Reading the inventory

- Active/wired means an implemented caller or startup path exists, not proof that production has run it.
- Conditional means a configuration/credential/eligibility gate controls whether it runs. Secret values were not read.
- Manual-only actions are listed to distinguish them from unattended jobs; automatic downstream effects are included.
- Orphan, retired, missing, and test-only behavior is separated from operational inventory.
- Shared delivery/scheduler infrastructure is not a separate business automation for every caller. Cross-domain references intentionally document shared chains rather than additional independent runners.

## Proposed registry location — not created

server/automations/ is consistent with the current server-side TypeScript layout. Proposed domain directories: messaging/, payments/, bookings/, moderation/, ai/, provider/, scheduled/. Domain-specific scheduled automations should stay in their business domain; scheduled/ should hold cross-domain operational/cache/cleanup work. This is a location proposal only, pending user confirmation. Existing server/jobs/ and server/services/ contain real action implementations; discovery does not authorize moving or replacing them. No stable registry IDs or nodes have been introduced.

## Confirmed reliability findings

- Scheduled external endpoints, warm-process timers, and GitHub cron backstops coexist. Replit Scheduled Deployment provisioning/firing is not established from this repository.
- The existing shared background runner prevents same-name overlap only inside one process, caps concurrent work, and retries thrown transient database errors; it is not a durable queue or distributed idempotency store.
- Some automation-specific SQL transitions, unique identities, or ledgers are durable; other flows rely on check-then-write or logging alone.
- Email outbox delivery has bounded retry/dead-state handling. Several direct email and webhook downstream paths acknowledge/log failures without durable recovery.
- Earnings eligibility release is automatic; seller payout transfer initiation is manual.
- Current cart payment promotion has no traveler confirmation-email producer found. Legacy booking confirmation emails do exist.
- No automatic report-to-suspension, expert reassignment, dormant-user campaign, post-booking review solicitation, or recurring price-drop watcher was found.
- Timed expiry rules are not always jobs: cancellation cutoffs, quote expiry, and token expiry often apply at request time.

## Evidence reconciliation notes

Two points were reconciled after overlapping domain scans: canonical provider-alert producers are not traveler-confirmation producers; the active daily admin digest is the production scheduler service, not application-decision routes or the manual digest implementation. Corrected messaging entries below supersede those initial interpretations. The booking-expiry SQL was directly inspected: it scans and updates legacy bookings, not service_bookings; service-booking no-response notices ride the same pass but are separate.

## Platform scheduling check

Official Replit documentation describes Scheduled Deployments as finite commands running on cron-like schedules, Autoscale as scaling down when idle, and Reserved VM as continuously running. Therefore warm-process timers alone cannot establish scheduled reliability for this Autoscale application. The repository already documents an external scheduled runner calling the shared internal endpoints, but explicitly leaves provisioning to an operator. No deployment was created or changed.

Official source: https://docs.replit.com/features/publishing/deployment-types

### Cross-domain overlaps / registry seams

1. Payment success can feed checkout promotion → completion/earning mint → hold/release eligibility → explicitly admin-triggered transfer; dispute/out-of-band-refund signals can stop the middle/release steps. Stripe reconciliation audits same payment/refund facts and only narrow handoff repairs.
2. `charge.refunded` is shared by manual in-app refund issuance and outside-dashboard refunds; it audits every refund but only foreign refunds trigger safety stamp/earnings hold. Refund issuer’s fee reversal/audit and webhook use shared recorder. It intentionally does not claw back paid-out sums.
3. Booking auto-completion and hourly earning release are separate automations; “released” is not “paid”. Payout is manual, and uncertain Stripe result stays processing.
4. Identity `verified` and Connect `account.updated` business `verified` both call listing activation; full predicate protects listings, but the callbacks are separate event sources and Identity’s error/retry behavior is weaker.
5. Affiliate zero-amount entry → report token/fuzzy matcher → partner-reported commission adoption and booking-request confirmation → ordinary held earnings flow. No affiliate money/payout webhook found; report matching is the reconciliation boundary.
6. Platform vs Connect webhook endpoints have separate signing secrets/event workflows. Platform payment PIs and platform disputes/bank payouts use platform route; Connect route processes connected account status/transfers and connected PI/revenue variants. Do not assume all event types overlap or share `webhook_events.processed` ownership.

# Scheduled operations and runtime wiring

## Findings

### Startup and runner topology
- `server/index.ts:746-815` is the main startup point (`onServerReady`): it starts cache refresh, checkout-claim sweep, booking expiry, admin digest, earnings release, Stripe Connect reminders, FX refresh, trip-card handover, stale itinerary sweep, email outbox, occasion drafts, evidence scoring, and DMO ingestion. `server/index.ts:821-928` additionally arms delayed/daily passes, a once-per-boot DMO extraction warmup, and nightly QA.
- There is a second scheduler start point: `server/routes/content.routes.ts:7002-7003` calls `travelPulseScheduler.start()` during route registration; `server/services/travelpulse-scheduler.service.ts:49-79` schedules its delayed first pass then 24-hour interval.
- Shared `runBackgroundJob` (`server/services/background-job-runner.ts:82-137`) skips same-name overlap and skips when the four-job concurrent cap is full. It retries thrown transient database/connection failures up to the configured default three attempts with exponential backoff; other errors throw to callers. Jobs that catch and return `{error}` do not get runner-level retries. Many scheduler wrappers catch/log failures, so permanent failures are generally logged, not automatically retried later except on the next cadence.
- Internal `runJob` records heartbeats only for real, successful passes and leaves skips unstamped (`server/routes/internal.routes.ts:86-150`). The HTTP endpoints return failures for throws or job-specific failure results. The CI poster additionally requires HTTP 200 + JSON + `{ok:true}`; it waits for `/api/ready`, retries only 404/503 up to three times (5/10/20 sec), and does not retry 401/500 (`scripts/ci/post-internal-jobs.sh:12-26,64-103`).

### External cron wiring and actual Replit deployment status
- `.github/workflows/jobs-cron.yml:63-93` is a repo-configured `*/15 * * * *` backup trigger plus manual dispatch. It runs `scripts/ci/post-internal-jobs.sh --due`; the due-bucket table and arithmetic are in `scripts/ci/post-internal-jobs.sh:297-357`: backstops/hourly every run, four-hourly on UTC hours divisible by 4, six-hourly divisible by 6, daily throughout UTC hour 09. - **No actual Replit Scheduled Deployment configuration/entrypoint is present in the repository.** `.replit:37-46` configures an Autoscale web deployment (`npm start`), not a scheduled deployment. `docs/ops/REPLIT_SCHEDULED_JOBS.md:1-5,25-43` explicitly says operator setup is required and the deployment is not created by the repo; it prescribes a second Repl and command. Thus the code documents an intended authoritative Replit schedule, but its existence/firing cannot be established from repository evidence. The repo-configured GitHub cron is real configuration; actual GitHub delivery is likewise not proven by source.
- `JOB_CADENCE` is the health roster (`server/routes/internal.routes.ts:153-186,330-340`); it says health measures “last cron-driven success,” not the app’s warm-instance timers. The roster includes jobs-cron’s eleven routes plus occasion drafts. `/api/ready` is a seeding/service-key readiness probe, not scheduler liveness (`server/index.ts:174-235`). Static scheduler liveness is explicitly only a source check, not evidence a timer fired (`server/services/runtime-health.service.ts:371-423`).
