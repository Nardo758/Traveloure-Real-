02

Where grounding happens — one fail-closed pass at build time

After Claude returns the free-text day plan (the existing generate-itinerary route), a resolver runs over each item before the rows are written. It's the net-new heart of Phase 1 — and it reuses the honest-match posture the optimizer already proved.

Step 1 · load

Destination catalog + DMO places

The existing loadOptimizerCatalog(destination) (approved + active + destination-scoped) plus the market's DMO extracted places. Both already exist.

Step 2 · match

Normalized name + geo/category

Each AI item's title/location is matched against those two sets — the same normalized-name + confidence composite the DMO resolution waterfall already uses.

Step 3 · gate

Confidence threshold, fail-closed

Above threshold → link (catalog id or DMO place id + its coords). Below → no link. An invented or ambiguous match is never accepted.

Step 4 · write

Stamp the link on the item

Catalog match → providerServiceId (already exists) + real coords. DMO match → dmoExtractedPlaceId (net-new column) + its coords. No match → item as-is, origin='ai'.

Fail-closed is the whole safety story (§13). The optimizer already honors an AI-returned service id only when it matches a service actually put in front of the AI — "invented, empty, or self-created stays NULL." Phase 1 grounds by the same rule: a link is written only when a real row matches at confidence; otherwise the item stays an honest suggestion. The traveler never sees a booking button that goes nowhere or a pin the platform guessed.

04

Four calls for you

Each has a recommended default; none is obvious enough to decide silently.

Q1

When does grounding run?

Automatically as part of every AI generate, or a separate "ground this slip" button the traveler presses?

Recommend: automatic, in the same build pass — one step, no extra UI, and re-generate re-grounds.

Q2

Does a catalog match auto-add to cart?

A grounded bookable item could land in the cart, or just be markable bookable and left to the traveler.

Recommend: mark bookable, never auto-cart — the traveler chooses to add (consent; no surprise charges).

Q3

Are DMO places bookable?

DMO places aren't platform inventory. Link them as informational (map pin + official/ticketing link), not as a "book on Traveloure" CTA?

Recommend: informational only in Phase 1 — real pin + official link, never a platform booking button (that's a §16 affiliate question, Phase 2).

Q4

How conservative is the match?

A high threshold grounds fewer items but never wrongly; a low one grounds more but risks a bad link.

Recommend: conservative/high — fail-closed. An honest "suggestion" beats a wrong booking link every time (§13).

05

The Phase 1 / Phase 2 line

Phase 1 grounds only to things that are safe and in-house. Affiliate/partner inventory is deliberately out until Phase 2, where it rides the §16 booking-agent rail.

Phase 1 — this mock

Catalog + DMO

Catalog = in-platform bookable services (a real listing, a real charge, add-to-cart). DMO = recognized places we already extracted (map pin + official link, informational). Both are honest, in-house, and need no third-party booking path.

Phase 2 — filed

Affiliate + registry (§16-safe)

Partner/affiliate inventory grounds through the booking-agent rail (/api/affiliate-booking-requests) — never a raw off-site link. Separate lane; needs the §16 rail wired into the AI build. Not built here.
