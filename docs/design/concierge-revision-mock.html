Mockup for sign-off · Ready-Made purchase support

Concierge Revision — recourse without a destructive refund

Ratified model: a Ready-Made purchase carries no self-serve refund. Instead every purchase includes one consultation and one revision from the expert who built it. The 7-day escrow window becomes the expert's service deadline, and an admin-mediated refund stays available for genuine disputes. This replaces the old "refund deletes the trip" path — which destroyed the buyer's own additions and orphaned live paid bookings (fixed separately in the hardening PR).

✓ Purchased → 1 Revision available → 2 Requested → 3 In progress → 4 Delivered

State lives on the purchase row (readyMadePurchases.revision_status, additive-nullable) — one entitlement per purchase. Escrow releases the expert's earning only after Delivered, or on the admin dispute path.

It's the buyer's own trip now, so changes ride the existing Suggest→approve flow — the buyer stays in control.

Why Suggest, not silent edit: the clone is the buyer's own trip. The expert holds temporary advisor write access, but material changes surface as suggestions the buyer approves — so nobody's plan changes under them, and "1 revision" has a clear done-line (approved = Delivered).

Refund here is safe: it runs the same ledger reversal, but the clone-delete honors the hardening guard — a buyer who has since booked real services keeps their trip and those bookings; only the ready-made charge is returned. The admin decides; the system never auto-destroys.

What this reuses vs. what's new

Almost all the machinery exists — an expert editing a traveler's trip is a solved problem (advisor access + the Suggest flow). The new surface is thin: an entitlement state, a request action, and the admin dispute view.

Reuses

Expert edit access

tripExpertAdvisors with a WRITE-access status (§12) grants the selling expert temporary edit rights on the buyer's clone — the same grant assigned advisors already hold.

Reuses

Inbox → Assigned Trips

The request appears in the queue experts already work; no new expert surface.

Reuses

Suggest → approve

POST /api/trips/:id/suggestions — the expert proposes, the buyer approves. The buyer stays in control of their own trip.

Reuses

Consultation = chat

The existing /chat thread system, scoped to the purchase. No new messaging.

Reuses

Escrow as SLA

The ready_made_sale hold already exists; its meaning shifts from "refund window" to "expert must engage before earning releases."

New

Entitlement state

readyMadePurchases.revision_status + request note (additive-nullable, declared in shared/schema.ts, no CHECK — publish-trap rule). One revision per purchase.

New

Request + admin dispute

Buyer "Request my revision" action; admin dispute list under the §2 blanket guard, refunding via the existing ledger + the hardening delete-guard.

New

Listing promise

Ready-Made cards/detail state "includes 1 consult + 1 revision" so buyers know before they buy — and it becomes a real selling point.
