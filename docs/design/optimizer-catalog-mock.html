Codebase audit · AI slip optimization

What the Optimizer Sees

A file-and-line audit of every data source the AI trip optimizer reads when it optimizes a slip — the trip inputs, the traveler profiling built from selections, the service catalog it draws from, the city intelligence, the LLM call itself, and the boundaries it never crosses.

Audited 2026-08-22 at main 22a015bb · sources: server/itinerary-optimizer.ts · optimizer-baseline.service.ts · traveler-profile.service.ts · routes.ts §8406–8909 · transport-leg-calculator.ts · smart-sequencing.service.ts · travelpulse.service.ts · optimization-fee.service.ts

In one paragraph: the optimizer reads a deliberately narrow slice — seven basics per still-planned item, paid items as "plan around this" constraints, expert-held items invisible. It ranks a flat 100-row pull of active services (no destination or approval filter) by an LLM-written trending list plus a profile inferred from the traveler's own selections, shows the AI the top 20, and asks Grok-3 (Claude Sonnet 4.5 fallback) for exactly two alternative plans chosen from a fixed strategy matrix. The server then re-sequences the days with a hand-written wellness rulebook and scores 60% AI self-score / 40% sequencing. It never touches money — the fee is resolved and gated before the AI is ever called.

01The run, end to end

Slip: ✨ Optimize this plan→ Fee gate (pay / free 24h re-run)→ Read trip + profile + catalog + city intel→ LLM: 2 variants→ Strip echoes · re-sequence · score→ Review board (you confirm)

Generation is fire-and-forget background work — the page polls every 2s until the variants land. A first run and a re-run are not the same optimizer: the create path passes no trip preferences, no anchors, no day boundaries, so every first optimization runs the default strategy pair. Only re-runs see event type, budget, travel styles, and dislike chips.

02Trip inputs — what it reads from your slip

Per item, exactly seven things reach the AI: Day · time slot · name · $price · duration · location name (+ type). No coordinates, no ratings, no descriptions of your items, no expert notes. Marquee items (helicopter / private / yacht / VIP keywords, or any non-commodity item ≥ $300) join a PROTECTED block the AI must keep verbatim. Empty trip days get an explicit "fill this day" instruction.

03Traveler profiling — learned from selections

The layer that personalizes optimization. Stored on users.preferences.travelerProfile; explicit answers always beat inferred signals, and nothing is fabricated when neither exists.

Three steering channels: (1) a prompt section describing you to the AI (with an instruction to never change prices); (2) transport scoring knobs — mobility "limited/wheelchair" forces accessible modes and ≤5-min walks; (3) catalog re-ranking — dietary keyword match +2, budget-band price-tercile match +1. Dislike chips also steer the re-run directly: too_expensive → Budget Optimizer, too_packed → Relaxed Pace, wrong_areas → Neighbourhood Regroup, wrong_vibe → Local Character — chips outrank every other strategy signal.

04Catalog access — the inventory it can offer

One query: the first 100 provider_services rows where status='active' — no destination filter, no approval-status filter, no availability check, no ordering. The list is re-ranked (trending first, then profile fit) and the top 20 are shown to the AI as id|name|type|$price|rating★|location. Service-ID validation accepts any of the 100.

These become prompt guidance: peak-crowd hours to avoid, events with crowd impact, seasonal weather. No live weather, no live crowds, no live pricing, no availability APIs are in the path. The review page's "Trending now / Popular around your dates" strip draws from the same family of signals.

06The LLM call

  • Grok-3 first (temperature 0.7, JSON mode, 8K tokens) → Claude Sonnet 4.5 fallback (16K tokens). Truncated Grok responses fail over.
  • Always exactly two AI variants + your plan persisted as the baseline variant.
  • Strategy matrix, priority order: dislike chips → event type (romance/corporate) → budget ≥ $8,000 → travel style (culinary / adventure / wellness) → default Budget Optimizer + Experience Enhancer.
  • Rules given to the model: differ in ≥40% of line items, preserve PROTECTED items exactly, respond in strict JSON.
  • Cost tracking: only the Anthropic fallback writes ai_cost_tracking — Grok runs are never cost-tracked, and rows carry no user id.

07After the AI — deterministic post-processing

  • Echo strip: any variant item matching a purchased commitment is deleted before metrics.
  • Must-retain enforcement: a variant missing a checkout-bound item is rejected outright.
  • Smart sequencing: a hand-written rulebook reorders each day (spa after adventure, no swimming right after meals, culture in mornings, golden hour, nightlife last…). Final score = 60% AI self-score + 40% sequencing score.
  • Metrics: balance / wellness / pace / diversity computed from category minutes; assumes a 14-hour waking day and 4–6 activities as optimal pace.
  • Upsells: computed on read — active services in the city matching event/style keywords, best-rated, max 3. Same missing approval filter.
  • Segmentation proposal: recommendation-only, derived from item locations and dates.

08What it does NOT see

  • Expert domain: with_expert items, per-item Expert Notes, trip-level expert notes.
  • Party data: trip participants, and their accessibility_needs / mobility_level — the only accessibility signal is the account owner's own profile setting, which is a different person's answer.
  • Item richness it could use but doesn't: coordinates, energy level, weather-dependence, flexibility flags, conflicts, participant limits.
  • Supply truth: vendor availability slots, lead times, concurrent-booking caps, pricing tiers, meeting points, cancellation policy — the AI can schedule a service at a time it cannot actually be delivered.
  • Anything live: weather, crowds, prices, flight/hotel inventory.

09Findings that need a decision

DefectUnapproved listings can reach travelers through optimization

The catalog pull filters status='active' only — never approval_status='approved' — unlike every other public read (the canonical gate checks both). Since listings are born submitted, an unapproved service can be offered to the AI, placed in a variant, and surfaced by upsells. The in-code comment claiming the list is pre-approved is wrong at both call sites. One-line filter fix, both endpoints + upsells.

DefectAI-authored prices can be read back as trusted server prices

Variant item prices are written verbatim from the model's JSON — never cross-checked against the catalog row even when the service link resolves. Apply-to-cart is safe (it re-derives from the catalog and skips unlinked items), but booking.service.ts has a fallback that reads itinerary_variant_items.price as the server-side price under a §14 comment — true against the client, but the value's origin is the LLM. Money-provenance review recommended.

Inert featureThe transport-leg engine never runs — travel times are LLM guesses

Leg computation is real (haversine ×1.3, per-city mode profiles, accessibility filtering) but gated on variant items having coordinates — and nothing ever writes coordinates onto variant items. So legs are never computed and every "travel time" figure is the model's self-reported number. Direct consequence for the review-first slip we just shipped: the "shorter drive time" preview chip will honestly omit (§13) on every proposal until coordinates are wired — the money chip and trending/seasonal strip are unaffected. Fix: carry lat/lng from the catalog row / itinerary item onto variant items.

GapNo destination filter on the catalog pull

An arbitrary 100 rows, any market — a Kyoto trip can be offered Edinburgh inventory, and popular markets can crowd each other out of the 100. Trending/profile re-ranking operates on whatever happened to arrive.

GapFirst runs ignore every preference signal

The create path passes no trip preferences — event type, budget, travel styles, and chips only reach the strategy matrix on re-runs. Every traveler's first paid optimization is the same default pair.

NoteGrok costs untracked · participant accessibility unused · availability unchecked

Grok-first means most successful runs log $0 AI cost. Participant-level accessibility answers exist but never steer optimization. No availability check means variants can propose undeliverable time slots — surfaced honestly at booking time, not at proposal time.

10Money boundary — clean

The optimizer imports no fee logic and makes no charge decisions. The optimization fee is resolved by optimization-fee.service.ts (event-type row → tier default, deterministic, fail-safe) and enforced by the payment gates in the route handlers — free 24h re-run window, verified PaymentIntent with server-side fee recompute, atomic single-spend claim — all before any AI call. The one caveat is the AI-price read-back path flagged above.
