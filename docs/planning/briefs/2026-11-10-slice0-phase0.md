## Findings that need a decision

**F1 — Bot audit rows cannot go in `access_audit_logs`.** `access_audit_logs.actor_id` is `NOT NULL REFERENCES users(id) ON DELETE CASCADE` (`shared/schema.ts`). A bot is not a `users` row, which is why `bot.routes.ts` writes only a log line today. A v2 asks for `actorId = the bot id` in that table.
- Option A: make `actor_id` nullable and add `actor_bot_id` (FK `bot_accounts`). It changes a NOT NULL on a table about 10 readers assume is non-null (`admin-query.service.ts`, `audit-log-query.ts`, `admin-audit-digest.ts`, the admin digest "by person").
- Option B: a sibling append-only table `bot_audit_logs` (`bot_id` FK `bot_accounts`, `action` bot.read / bot.propose / bot.flag, `resource_type`, `resource_id`, `metadata` with method, path and scope, `created_at`). The "filter by bot" read is `GET /api/admin/bot-audit?botId=`; the retention prune deletes only these rows.
- **Default: B.** It is born empty, changes no existing table, and the prune cannot touch a human's audit row. The `recordBotAudit` writer and the never-fail rule (§15b) are as A v2 states.

**F2 — The owner's id cannot be in a committed migration.** A v2 puts "the owner-role statement from Leon's PR comment" in the migration, and the rule is that the id never goes in a doc or commit. A migration file is a commit.
- **Default:** the committed migration carries everything except that statement. The owner statement is one line Leon runs by hand in each database's Shell, right after the publish that applies the migration. The PR carries it with a placeholder:

  ```sql
  UPDATE users SET role = 'owner' WHERE id = '<Leon's users.id from his PR comment>' AND role IN ('admin', 'platform_admin');
  ```

- Window: until it runs there is no owner, so the owner-only routes (money, fee bands, grants, bot keys, settings) refuse everyone. Run it right after publish. Staging needs the same statement.
- **Correction (found during the build):** an `ADMIN_EMAIL` boot bootstrap does exist (`server/index.ts`). It promoted that address to `admin` and would have demoted an owner. It now promotes only an account that is not already `owner`, `platform_admin` or `admin`, and promotes to `platform_admin`. It never creates an owner, so the hand-run statement above stays the only way an owner is set.

**F3 — A listing and a provider form have no market column.** `provider_services` has `location` (free text, default `'Unknown'`) and no `market_slug`. `service_provider_forms` has free-text `city`/`country`. A v2 resolves "the resource's market from its row".
- **Default:** one resolver in `server/services/staff-scope.ts`.
  - A listing's market is `resolveMarketSlug(location)`, else its owner's provider-form city.
  - A provider form's market is `resolveMarketSlug(city)`.
  - A bot proposal uses `bot_proposals.market`, and a place fact uses `place_facts.market`.
  - A row whose market does not resolve is in no market: a scoped role gets 404 and owner / platform_admin act as today (§13, never guessed).

**F4 — Only two of the issue queue's four reads exist.** Addendum A names expired facts, unclaimed questions (slice 7), provider gaps (`listing_gap`, slice 1) and message reports. `listing_gap` and `expert_questions` do not exist on main.
- **Default:** the queue ships with the reads that exist: expired `place_facts` by market, and pending `bot_proposals` by market (provenance included). The other two join when slices 1 and 7 land.
- Message reports carry no market (`message_reports` has reporter and reported user only), so they are not market-scoped. They stay on the moderator / owner / platform_admin routes they use today and are left out of a regional manager's queue.

**F5 — The Ops Bot's flag / triage write has nowhere to land yet.** Bots are refused on every `/api/admin` path, so the Ops Bot works through `/api/bot/*`. A "flag" is a `listing_gap` proposal (slice 1, not built), and "triage" has no column in A v2's migration list.
- **Default:** a new scope `queue:read` and `GET /api/bot/queue`. It returns the issue queue above as ids, kinds, markets and ages, with no user id, email or proposal body. Flag and triage writes land in slice 1 with `listing_gap`. The scope list is stated so they cannot be granted early.

**F6 — "Every /api/admin route denied except propose/flag."** Propose and flag are on `/api/bot/*`, not `/api/admin`.
- **Default:** the route walk sends a bot token to every `/api/admin` route and expects refusal on all of them, including feature-flag and `platform_settings` writes. A second walk sends it to every `/api/bot` route and expects only the scoped read / propose routes to answer.

**F7 — 263 hard-coded `role === "admin"` checks.** 183 are in `admin.routes.ts`; the rest are in about 40 other files, including client.
- **Default:** one helper, `isAdminRole(role)` (owner, platform_admin, admin), replaces them mechanically, plus `isOwnerRole`. The blanket guard is where owner-only routes are refused to platform_admin. A handler that passes a platform_admin today keeps passing one, so no route's behaviour moves except through the guard map.

**F8 — UI strings.** A v2 lists admin-only strings (role names, Assigned markets, Awaiting owner sign-off, Confirm, Proposed by {bot}, Assigned to, Filter by bot). The rule is no new UI string without "Wording approved — Leon".
- **Default:** this PR is server and API only. Payloads carry the data (role, markets, `proposedBy`, `assignedTo`, the bot filter), and the screens follow once the strings are stamped.
