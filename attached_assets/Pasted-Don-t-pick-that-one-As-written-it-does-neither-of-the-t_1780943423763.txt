Don't pick that one. As written it does **neither** of the two things the strand needs, and force-pushes for nothing.

**Why it fails:**
1. **It rebases LB onto a `main` that doesn't have Patch A.** The whole premise of "rebase to inherit the client half" only works once Patch A is actually on `origin/main` — and we just confirmed it isn't (`3ddc5cc` has no `bookMutation`, Book button still bare at `:246`). Rebase onto today's main inherits **nothing** strand-related.
2. **It never applies Patch B.** A rebase replays LB's existing commits on top of main; it adds no new code. After running it, LB still has **zero** strand fix — client *and* server both absent.
3. **`--force-with-lease` rewrites your 7-ahead LB** (incl. Master-Brief 5.3) and can surface unrelated conflicts — all for no strand gain.

So you'd do a risky history rewrite and end up exactly where you started.

**Pick this instead** — put **both** halves on LB (it owns both files per the pin), co-located so the gate runs on one tree, and merge delivers them to main atomically. No rebase, no force-push needed:

```bash
git fetch origin claude/laughing-bardeen-KyTUY
git checkout claude/laughing-bardeen-KyTUY
git pull --ff-only origin claude/laughing-bardeen-KyTUY   # sync with remote LB tip

# apply Patch A → client/src/components/plancard/TransportSection.tsx
# apply Patch B → server/routes/transport-hub.routes.ts
git add client/src/components/plancard/TransportSection.tsx server/routes/transport-hub.routes.ts
git commit -m "fix(transport): wire platform Book CTA + resolve variantId via leg (strand)"

git push origin claude/laughing-bardeen-KyTUY            # plain push — no --force
```

Then in PR #46: **Update branch** if it's behind main (that's a merge, not a rebase — no force-push), resolve any conflicts, run gate B (populate `/options` first → `SELECT … variant_id IS NULL` → `POST …/book` → 200 + `checkoutUrl`), then merge.

**Why both-on-LB beats client-on-main + rebase:**
- Keeps the **pin honest** — `TransportSection.tsx` is LB-owned, so it shouldn't get a direct main edit anyway.
- **One tree to gate** — both halves present together, no half-on-main/half-on-LB window.
- **Atomic merge** — #46 lands both on main at once; nothing dangles if a step stalls.
- **No force-push** — you're adding a commit, not rewriting history.

If you specifically want the client half on `main` independently, the *only* way the rebase makes sense is: **push Patch A to `origin/main` first, then** rebase LB, **then still apply Patch B to LB** — three steps, more moving parts, and you're force-pushing. The both-on-LB path avoids all of it.

One caveat either way: your local workspace may already hold a `bookMutation` (the arg-order version you fixed). Before applying Patch A, diff against it so you don't double-add — reconcile to the single corrected version, then commit on LB.
