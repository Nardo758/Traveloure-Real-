============================================================
SURFACE 1 — AUTHENTICATION & SESSION
============================================================
Randomize each loop: which account, which device/tab combo, timing.

- Login with credential edge cases: mixed-case email, whitespace-
  padded password, already-registered email with different casing
- Password reset: token reuse after consumption, token expiry 
  enforcement, token guessability (is it a short/predictable value 
  or a real cryptographic token?)
- Multi-device/multi-tab session behavior: log in on device A, 
  change password — confirm device A's session is actually 
  invalidated, not just device B's new login working
- "Logout everywhere" (if it exists) — confirm it actually kills all 
  active sessions, not just the current one
- Login rate limiting / brute-force resistance — randomize attempt 
  count and timing pattern each loop
- JWT/session tampering (if JWT-based): modify role or user id 
  client-side, replay an old/expired token, confirm server rejects it

============================================================
SURFACE 2 — AUTHORIZATION / IDOR SWEEP
============================================================
For EVERY endpoint that takes a resource ID — bookings, messages, 
reviews, payouts, provider applications, profile data, admin actions 
— rotate which resource type and which ID pattern gets tested each 
loop:

- As User A, attempt to read/modify/delete User B's resource by 
  incrementing, guessing, or randomizing the resource ID
- Same test unauthenticated (no token at all)
- Admin-only endpoints tested with a non-admin token, then with a 
  provider/expert token, then with no token
- Randomize ID guessing strategy each loop: sequential increment, 
  random UUID-adjacent guess, ID from a different resource type 
  reused where type-confusion might slip through

============================================================
SURFACE 3 — INPUT VALIDATION / INJECTION SWEEP (site-wide, beyond 
messaging which was already tested)
============================================================
Cover every remaining input surface: signup/profile forms, review 
submission, provider/expert application form, search bar, contact/
support form, itinerary AI prompt input, admin panel forms.

Rotate which input class gets tested on which field each loop — 
don't run the same class everywhere every time:
- SQL injection payloads (', OR 1=1--, UNION SELECT, etc.)
- XSS payloads — script tags, event handlers, encoded/obfuscated 
  variants, markdown/HTML injection in free-text fields (reviews, 
  messages, application bios)
- Path traversal / command injection on any field touching filenames
- Max-length overflow, null bytes, zero-width/RTL/emoji unicode
- Malformed/boundary dates and numbers (negative price, decimal 
  quantities, far-future/past dates)

RESULT per field: Field | Input class | Expected | Actual | Pass/Fail
