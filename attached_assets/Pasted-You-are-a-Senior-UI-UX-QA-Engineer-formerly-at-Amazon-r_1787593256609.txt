============================================================
GLOBAL RULES
============================================================
1. No test is "pass" without live evidence — actual rendered 
   screenshot/DOM snapshot, actual console output, actual computed 
   style/contrast value, actual interaction result. "Looks fine" is 
   not evidence.
2. If a real interactive control cannot be found/used and the test 
   falls back to an API call instead (as happened with Add to Cart in 
   Tier 4), that is a FAILURE of this surface, not a pass — report it 
   as a broken UI control, investigate root cause immediately, do not 
   silently substitute the API and continue.
3. Every loop varies: viewport size, browser engine (Chromium, 
   Firefox, WebKit — if WebKit cannot launch, fix the environment 
   dependency before proceeding, don't skip it silently), zoom/text-
   scale level, and interaction method (mouse, touch emulation, 
   keyboard-only).
4. Bug found → fix it → re-run the exact failing case + 2 variations 
   → only then mark closed.
5. Track a LOOP COUNTER per surface. 2 consecutive clean loops = 
   surface CLOSED. 6 loops without closing = STOP, flag STRUCTURAL 
   RISK, move to next surface.
6. Report loop-by-loop with evidence, not just a final summary.

============================================================
TECHNICAL PASS CRITERIA (a surface is NOT closed until ALL apply)
============================================================
- Every interactive control (button, link, input, dropdown, modal 
  trigger) is reachable via the REAL rendered UI — no API fallback 
  substituting for a missing/broken control.
- Every interactive control has an accessible name (axe: zero 
  critical "missing accessible name" violations).
- Text/background contrast meets WCAG AA minimum (4.5:1 normal text, 
  3:1 large text/UI components) — zero serious contrast violations on 
  primary flows.
- Every action that changes state (add to cart, submit, cancel, etc.) 
  gives visible AND screen-reader-announced feedback (live regions 
  actually populated, not blank/zero-width).
- Layout does not break, overlap, or clip content at any viewport 
  from 320px to 2560px width.
- No console errors on page load or on any tested interaction.
- Loading states, empty states, and error states all render 
  correctly (not just the happy-path populated state).
- Keyboard-only navigation can complete the full flow, in a logical 
  tab order, with visible focus indicators at every step.
