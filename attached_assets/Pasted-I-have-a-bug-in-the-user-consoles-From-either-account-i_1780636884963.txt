This one's almost certainly a routing-prefix problem, and the route map tells the story: every role surface is path-prefixed (/expert/*, /provider/*, /admin/*) with access gated by route, but Messages has only one route — the un-prefixed traveler /messages (and the shared /chat "Expert Chat" page in your screenshot). There's no /expert/messages or /provider/messages in the architecture.

So the most likely root cause: your active console/role is derived from the URL path prefix, and the Messages item in all three sidebars points at the same un-prefixed route. The moment you navigate from /expert/... to /messages (or /chat), the path no longer starts with /expert, the role inference recomputes, and you land back in the default (traveler/user) console. That's exactly why it's Messages specifically and not the other items — the per-console sidebars prefix their own links, but Messages is the one hardcoded to the shared route.

Three greps confirm or kill it in about a minute:

How is the active role derived? Search for useRole / activeRole / activeConsole / currentRole. If it reads useLocation() / pathname rather than a context or store, that's the smoking gun — role is a function of the URL.
What does the Messages link point to? In the sidebar/nav component, find the Messages item's target. If it's a bare /messages or /chat with no role prefix, that's the trigger.
Does the chat page mutate role? Grep the messages/chat component and its layout for setRole / setActiveConsole. Less likely, but if the "Expert Chat" page sets context on mount, that's an alternate cause — messages should read role, never write it.
If it's #1 + #2 (the probable case), two fixes:

Durable: move active console into persistent state (context + localStorage) instead of deriving it from the path. This fixes the whole class — Cart, Notifications, Discover, and Credits are also un-prefixed top-level routes, so any of them would reset role the same way the moment you hit them from a console. Messages is just the one you happened to click.
Minimal: make the Messages link console-aware (role-scoped messages routes that preserve the prefix). Smaller change, but leaves the other un-prefixed routes as latent versions of the same bug.
I'd take the durable fix — path-derived role is the underlying defect, and patching one link just moves the bug.
