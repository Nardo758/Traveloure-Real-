# Traveloure — PlanCard (Itinerary Artifact) Spec

**Piece 3 of 4** (Expert itinerary-building services). **Type:** internal spec — *conformance pass* (spec ↔ build) **+ user-flow alignment**.
**Source of truth:** code @ `main` `68d588e` (2026-06-02). Refs are `file:line`. Prior spec: `SHAREABLE_ITINERARY_CARD_SPEC.md` (1,616 lines).
**What makes this doc different:** the PlanCard is the **only traveler-facing piece** in this set. It's the handoff boundary — what the expert *builds* in the Workspace (Piece 4) and what the user *consumes* in their own app flow. So this doc has to align with the **User application flow** (the Traveler journey from the Lead Journey doc), not just verify a component.

---

## 0. The headline

1. **The card is real and rich** — a composed component family with hero, metrics, day selector, activities, transport, an interactive map control center, change-log attribution, and native-maps handoff. The 1,616-line spec is largely honored.
2. **But the itinerary is rendered four different ways.** `PlanCard`, `DashboardPlanCard`, `ItineraryCard`, and the Workspace's bespoke renderer are four independent implementations of "show the itinerary," and capabilities are split across them (booking badges live in one, map layers in another). This is the central conformance problem.
3. **Three documented features are partially or not built:** the third map layer (expert notes), the reject half of accept/reject, and the platform-vs-affiliate booking badges (§5).

---

## 1. Where it lives in the User application flow

The PlanCard mounts at **four** points, each a different stage of the traveler journey (cross-ref Lead Journey doc T2–T7):

| Mount | Page | Journey stage | Card state at this stage |
|---|---|---|---|
| Dashboard card | `dashboard.tsx` → `DashboardPlanCard` | T2–T3 (has trips) | summary; pre-finalization |
| Trip detail | `trip-details.tsx` (`/trip/:id`) | T3–T6 (planning → delivered) | full editable card |
| Itinerary page | `itinerary.tsx` | T3–T6 | full card |
| Shared view | `itinerary-view.tsx` (`/trips/shared/:token`) | T7 (share / on-trip) | read-mostly, token-scoped |

**State is contingent on journey stage** — the card is not static:
- **Transport section populates only post-finalization** (the "transport is post-optimization" gate; Workflow doc §1). Pre-review the transport tab is empty by design.
- **Permissions are role-gated** (§4): the same card shows different affordances to owner vs expert vs friend.
- **Suggestions** (AI/expert) appear as `suggested`-status items the owner acts on — a user-flow state transition, not decoration.

So a correct reading of the PlanCard is "what does this card do **at stage X for role Y**," and that's how the build should be validated.

## 3. Data model & server contract

**Types** (`plancard-types.tsx`): `PlanCardTrip`, `PlanCardDay` (dayNum, date, label, energyProfile, activities, transports), `PlanCardActivity` (id, name, type, status, time, location, lat/lng, cost, comments, `changes[]`, `expertNote`), `PlanCardTransport` (mode, from/to, duration, cost, status, line, `suggestedBy`), `PlanCardChange` (who, role, type, what, when), `PlanCardMetrics`, `PlanCardStats`.

**Vocabularies:** activity types `dining | attraction | shopping | transport | accommodation`; statuses `confirmed | pending | suggested`; transport modes `walk | train | taxi | car | bus | shuttle | ferry | bicycle`; change roles `expert | friend | ai | owner` (color-coded); energy `relaxed | balanced | intense`. Three template skins: `travel`, `wedding` (incl. honeymoon/proposal), `corporate` — relabel activities/stats per event type (`getTemplateConfig`).

**Server contract** — `server/routes/plancard.routes.ts`:
- `GET /api/trips/:tripId/plancard` (`:36`) → `{ days, changeLog (capped at 10), metrics, stats }`.
- Plus comments + change-tracking endpoints (`:210`, `:269`, `:284`, `:334`) backing the attribution feed.

> **Conformance flag (data shape):** the server returns `metrics` as a raw `metricKey → value` **string map** (`:141`, `:182`), but the client `PlanCardMetrics` type expects named **numeric** fields (`traveloureScore`, `optimizationScore`, …). Verify the keys/types line up at the boundary — a silent mismatch here means metrics render blank.

## 4. Permission / collaborator model

Change attribution is first-class and role-colored (`CHANGE_DOT_COLORS`): **owner** (amber), **expert** (blue), **friend** (purple), **ai** (green). The `ChangeLogPanel` renders the who/what/when feed; `PlanCard` surfaces a pending-expert-changes count (`PlanCard.tsx:78`). Suggestions carry `suggestedBy` and render as "AI suggested" (green) / "Expert suggested" (purple) on transport legs.

This matches the documented model (owner full control, expert can edit/fill, friends comment/suggest) **at the attribution layer**. What's missing is the *action* layer — see reject, below.

## 5. Conformance findings — spec vs. build

| # | Documented | Built | Status |
|---|---|---|---|
| C1 | **3 map layers**: activity pins, transport routes, **expert notes** | MapControlCenter toggles **2** only (`activities`, `transport`); no notes layer | **Divergence** — `expertNote` exists as a field but has no map layer |
| C2 | **Accept/reject** for AI + expert suggestions | **Accept only** (`TransportSection:126`); no reject/decline/dismiss anywhere in `plancard/` | **Divergence** — half the flow is missing |
| C3 | Transport booking: green "Book on Traveloure" vs blue affiliate partner | Badges live in **`ItineraryCard`** (`partnerName`), **not** in PlanCard's TransportSection | **Split surface** — PlanCard shows suggestion attribution, not booking source |
| C4 | One portable card | **4 renderers** (PlanCard, DashboardPlanCard, ItineraryCard, Workspace) | **Fragmentation** — the meta-issue |
| C5 | Native maps deep-link handoff | Works via `@/lib/navigate` (waypoints+mode), **but** a second lib (`maps-platform.ts`) and an inline handler in `PlanCard.tsx:41` also exist; the no-waypoints branch passes `{lat:0,lng:0}` (`MapControlCenter:365/375`) | **Works but fragmented**; 0,0 fallback is a bug |
| C6 | Hero destination photo | `getDestinationPhotoUrl` → `source.unsplash.com` (discontinued service) | **Likely broken images** — swap the source |

**C4 is the one that matters most.** Capabilities are scattered: map layers only in PlanCard, booking badges only in ItineraryCard, the build view reimplemented in the Workspace. Any change to "the itinerary" must be made in up to four places, and they will drift (they already have — see C1/C3). This is the same divergence as Workspace flag #3, seen from the canonical user-facing side.

## 6. Recommendations

1. **Consolidate to one renderer.** Make `PlanCard` (+ its sections) the single itinerary surface; have Dashboard, Itinerary, shared-view, **and the Expert Workspace** all mount it with role/stage props. This closes Workspace flag #3 and conformance C4 in one move. Highest-value, largest effort.
2. **Build the reject half (C2)** and the **expert-notes map layer (C3/C1)** so the card matches its own spec and the attribution model has matching actions.
3. **Unify the booking-source badge (C3)** into the shared transport component so platform-vs-affiliate display is consistent wherever transport renders.
4. **Pick one maps handoff path (C5)**, delete the others, and fix the `{0,0}` fallback to use the geocoded destination.
5. **Replace the Unsplash source (C6).**
6. **Verify the metrics shape** at the `/plancard` boundary (§3).
