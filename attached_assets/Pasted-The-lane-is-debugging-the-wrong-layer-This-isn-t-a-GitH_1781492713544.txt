The lane is debugging the wrong layer. This isn't a GitHub ref / check-association problem — that whole "maybe it's the old workflow ref" thread is a rabbit hole. It's a **schema drift**, and there's a scope-leak angle underneath it that's the actual story.

Look at the column: **`preferred_currency` is a multi-currency column — that's Stage 2.** Stage 2 is *paused* until E2E-1 runs green. So a Stage 2 schema change has leaked backward into the E2E seed and is now blocking the Stage 1 gate that's supposed to run *before* multi-currency. That's a circular dependency created by scope creep, and it's exactly what the stage boundary exists to prevent.

So before touching the workflow, answer one question — grep your migrations:

**Does a migration actually create `preferred_currency`?**

- **No migration creates it** → it leaked into `schema.ts` + the seed without a migration. That's the drift. The fix is **strip `preferred_currency` from the E2E seed** — Journey 1 (discover → cart → payment) doesn't need a currency preference to run. That unblocks E2E-1 *and* restores the Stage 1/Stage 2 boundary. The column comes back when Stage 2 actually starts, with a real migration.
- **A migration does create it** → then it's legitimately landed, and the workflow's DB just isn't getting your migrations applied. Fix that (below), not the seed.

Either way, **kill the `drizzle-kit push --force` band-aid.** That's the wrong tool for your stack and it'll cause worse problems than the one it's patching. Your doctrine is migrations-as-canonical with chain-integrity tests — and `push --force` *bypasses the migration chain* to sync `schema.ts` straight to the DB. That means your E2E would validate against a schema your migrations never produce. It would hide exactly this class of drift forever: a column in `schema.ts` with no migration would "work" in CI (push creates it) while breaking in any environment that applies migrations — i.e., production. You'd be testing a schema you don't ship.

**The structural fix: build the E2E workflow's DB by running your migrations, then seed.** `migrate → seed → test`, not `push → seed → test`. That guarantees E2E tests the same schema production gets, and it doubles as a free migration-chain smoke test — if your migrations don't build a working DB, E2E goes red, which is a signal you *want*. It's slower than push by a few seconds; for a pre-launch product where migration correctness is load-bearing (your whole `fee_bands` story depends on it), that's the right trade.

So, concretely:
1. Grep migrations for `preferred_currency`. That branch decides seed-strip vs migrate-fix.
2. If it's unmigrated Stage 2 leakage (most likely): strip it from the seed, re-run E2E-1. That's your fastest path to the green baseline.
3. Replace `drizzle-kit push --force` in the workflow with `migrate → seed`.
4. When Stage 2 starts for real: add `preferred_currency` via a proper migration, update the seed, re-verify. Not before.

The reason you "keep having this problem" is that push-force keeps masking the drift instead of fixing it — every run papers over the same missing migration. Run migrations in CI and the drift surfaces once, loudly, where you can fix it.
