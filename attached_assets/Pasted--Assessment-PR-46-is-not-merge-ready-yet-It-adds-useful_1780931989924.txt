## Merge Readiness and Risk Assessment

### Blocking / important concerns

#### 1) Likely bug: `GET /api/admin/neighborhoods/:id` can expose experts from other markets
The detail endpoint loads experts by `neighborhood_id` only:

```ts
SELECT en.expert_id, en.is_lead, en.sort_order,
       u.first_name, u.last_name, u.email
FROM expert_neighborhoods en
JOIN users u ON u.id = en.expert_id
WHERE en.neighborhood_id = ${id}
ORDER BY en.is_lead DESC, en.sort_order ASC
```

But the lead assignment rules emphasize market correctness via `localExpertForms`. If stale or bad `expert_neighborhoods` rows already exist, this panel may show them as valid candidates/context without any annotation. That may be acceptable operationally, but if the intent is “admin-safe neighborhood spine,” this endpoint probably needs either:
- explicit filtering/flagging by market validity, or
- a UI-visible warning for experts whose form no longer matches the neighborhood city.

As written, the page may look authoritative while showing inconsistent data.

#### 2) The PR bundles two unrelated concerns
This PR mixes:
- **Neighborhood admin tooling**
- **Offering risk override schema migration**

That makes review and rollback harder. If the admin feature needs urgent iteration, the migration is unnecessary coupling. Unless this PR is intentionally part of a larger locked phase sequence, I’d strongly prefer splitting the migration into its own PR.

#### 3) No visible verification path
There are no fetched reviews or comments, and no supported check results surfaced. For a PR that adds:
- transaction-sensitive lead swap logic
- adjacency graph mutation logic
- production migration

I’d want at least some evidence of:
- route-level tests, or
- manual test notes in the PR description

Right now the PR body is empty, which lowers reviewer confidence.
